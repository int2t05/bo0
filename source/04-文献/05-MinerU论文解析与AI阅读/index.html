MinerU 论文解析与 AI 阅读流程

目的：明确 Zotero 原 PDF、LLM for Zotero 内置 MinerU 缓存、read4all Markdown 和外部 AI 的分工，并保留证据回查路径。 核验日期：2026-11-06。实测环境为 Windows 10、Zotero 10.0.7、Python 3.12、MinerU 4.1.7；AI 阅读插件最终选用 LLM for Zotero。 状态：read4all 云端 MinerU 已用新凭据通过 4 页测试 PDF 联通与解析校验；这只验证云端链路，不代表真实论文的解析质量。LLM for Zotero 在上游核验到 v3.9.16，本机安装版本和插件内 MinerU 设置仍需在 Zotero 界面确认。

结论

推荐把 Zotero 保留为原文、题录、标签和批注的权威库，把 MinerU 产物放在 Zotero 附件目录以外。AI 阅读使用解析后的 Markdown；核验事实时用页级结构数据跳回 Zotero 原 PDF。

Zotero 内的主阅读路径是：Zotero 原 PDF → LLM for Zotero 右侧论文对话/独立窗口 → 按章节提问并检查来源 → 引用跳回原 PDF。需要双栏重排时使用 Zotero Reading Mode。LLM for Zotero 可用内置 MinerU 解析和缓存为 Agent 提供结构化 Markdown、章节和页码提示；该缓存服务 AI 上下文，不是另一种 PDF 阅读器。

Codex 需要直接精读解析稿时，使用 read4all：convert_to_markdown 默认提交 MinerU 云端 V4 的 vlm 模型；返回 md_path 后，用 read_markdown 按 next_start_char 分段读取完整 Markdown。检查 engine_used 为 mineru 或 mineru-cache 且 fallback_reason 为空。read4all 本机缓存与 LLM for Zotero 的附件级 MinerU 缓存互不共享；不要重复解析同一论文，除非需要刷新或质量复核。

本机实测

测试对象是 Zotero 条目 GTEYDFKP《The Evolved Transformer》（arXiv 公开论文，PDF 14 页）。

路径 实际结果 结论
read4all → MinerU 云端 2026-11-06 使用更新后的本机凭据解析 4 页测试 PDF 成功：engine_used=mineru、972 字符、正文标题命中；随后通过 mineru-cache 和 read_markdown 验证缓存复用与直接分段读取。 云端认证、上传、轮询、ZIP 下载、缓存和直读链路均已连通。测试 PDF 是自动生成的 fixture，不是博士清单中的真实论文，因此不代表真实论文的版面质量评估。
本机 MinerU 4.1.7 Standard Windows 10 build 19045、i5-12400F（6 核/12 线程）、32 GB RAM、RTX 3060 Ti 8 GB。ONNX 选择 DirectML GPU，VLM 使用 llama.cpp。 本机解析成功，不上传 PDF。
本机输出结构 ZIP 0.86 MB；Markdown 64,313 字符、438 行；middle JSON 为 docvortex.middle 2.0，含 14 个页对象，page_idx 为 0–13；含 5 个表格块、2 个图表块、2 个图像块，ZIP 共 9 张图片；Markdown 含 33 组单美元行内公式。 ZIP 同时保留内容、图片和页级 JSON，比只拿 Markdown 更适合证据核验。这个本机样例数据来自此前的 MinerU 4.1.7 实测，不是本轮云端质量测试。
本机首次耗时 VLM 首次加载约 244.9 秒；模型推理 14 页耗时 30.85 秒，约 0.454 页/秒；从启动到 ZIP 写出约 5 分 35 秒，包含依赖与权重首次下载。 冷启动慢，模型和依赖缓存后不会再重复下载；stateless 的 mineru-kit parse 仍会重新推理，重复阅读应复用已有 ZIP。

表格数量是不同解析器的结构计数，不能直接当作准确率比较。图表、表格、公式是否被完整表达，仍要回 PDF 抽查。该样例的普通 Markdown 没有逐页标题；页码保存在 middle JSON，因此不可只保存或只交给 AI 一份 Markdown 后就声称每条结论有精确页码。

推荐操作流程

1. 从 Zotero 精确取得 PDF

用父条目的 Zotero key 查附件，确认题名、DOI、版本和首页与题录一致。不要根据 storage 随机目录名猜论文身份。

zotero-cli path <ZOTERO_ITEM_KEY>

若条目有多个附件，选择正确的 PDF 子附件。原 PDF 留在 Zotero storage，解析产物写到单独的本机目录，不放回 Zotero storage，也不要覆盖 PDF。

2. 用 MinerU 4.1.7 解析整篇论文

本机已通过 uvx 隔离运行，不修改系统 Python。当前实测命令：

uvx --python 3.12 --from "mineru==4.1.7" mineru-kit parse "<PDF_PATH>" --output "<OUTPUT_PATH>.zip" --format zip --tier standard --verbose

MinerU 4.1.7 的 mineru-kit parse 默认处理 PDF 全页；显式写 Standard 和 ZIP 能让质量档位、产物结构更明确。Standard 适合双栏期刊论文、表格与公式较多的精读文献；只需快速浏览可选 Flash；Advanced 留给 Standard 输出确实不足的个别文件。不要为已解析文件重复跑完整解析。

建议产物结构按 Zotero key 与 PDF 内容哈希隔离，例如：

<解析根目录>/
  <Zotero条目键>/
    <PDF哈希>/
      markdown.md
      middle_json.json
      structured_content.json
      images/
      manifest.json

保留整个 ZIP 或完整解压目录。Markdown 中的图片使用相对路径；移动 Markdown 而不移动 images 目录会断图。manifest 至少记录 Zotero 条目键、附件键、原 PDF 文件名、SHA-256、MinerU 版本、档位、页数、解析时间和输出文件清单。

3. 做解析质量门禁

read4all 云端转换后必须确认：

  • engine_used 是 mineru 或 mineru-cache；fallback_reason 为空。
  • page_count 与原 PDF 页数一致，Markdown 不为空，图片引用均能找到。
  • 表格、公式、双栏正文顺序、脚注和图注抽查正确。

本机 ZIP 转换后必须确认：

  • 命令以退出码 0 完成；ZIP 可正常打开，并有 Markdown、middle JSON、structured content 和 images。
  • middle JSON 的 is_full_document 为 true，页数与原 PDF 相同；schema/version 与实际文件内容匹配。
  • 页面索引用 middle JSON 的 page_idx。它从 0 开始；跳回 Zotero 时转换为 1-based 页号，即 Zotero 页号 = page_idx + 1。
  • Zotero CLI 可按页打开原文，例如 zotero-cli open --page <1_BASED_PAGE>。

如果关键公式、表格或图注有误，回原 PDF 手工核验；可只对问题页重解析或截图核对，不把错误 OCR 当成论文事实。

4. 交给 AI 阅读

在 Zotero 内使用 LLM for Zotero 时，直接对当前论文提问或点名章节；任务进度会显示实际读取范围，回答中的引用用于跳回原 PDF。插件内置 MinerU 的 Markdown 与图片缓存供 Agent 检索，不需要把文件路径再交给插件。

在 Codex 中精读时，先调用 read4all convert_to_markdown，再用 read_markdown 读取 Markdown。工具每次默认返回 12000 字符，并提供 next_start_char 续读位置；不应只根据 preview 判断完整论文。涉及图表时传入图像，或用 describe_images=True 为提取图生成文本描述；后者会增加模型调用和等待时间，通常不必在首次转换时默认开启。

提示模板：

只根据本论文解析产物回答。每个事实都标出 Zotero 条目键、
PDF 页号和章节/图表号。页号以原 PDF 为准；若原文印刷页不同，
两者分开写。区分作者声称、直接证据和你的推断。
找不到来源就写“未定位”。涉及表格、公式和图表时，指出需要
回原 PDF 核验的位置，不要把 OCR 缺失当成论文没有报告。

AI 生成后，用 middle JSON 的页对象定位候选证据，再打开 Zotero 原 PDF 页面核对。最终研究结论、阅读笔记和标签写回 Zotero 前仍需人工审阅。

云端与本地方案

方案 适用情况 优点 当前限制
LLM for Zotero + MinerU Cloud 希望在 Zotero 内对话/精读，并允许上传 PDF 到 MinerU 解析缓存按附件保存，供论文问答、Agent 分段读取和后续对话复用；AI 仍在 Zotero 阅读器中工作 需在 Zotero 插件设置中单独启用 MinerU 并验证个人 token；PDF 会发送到 MinerU，AI 上下文还会发送到所选模型服务。read4all 的 Codex key 不会自动同步到插件偏好设置。
read4all + MinerU Cloud 需要在 Codex 等 MCP 客户端直接读取解析稿，且允许把 PDF 上传到 MinerU vlm 精准解析、公式/表格开关开启、按内容哈希缓存；read_markdown 分段直读全文 本轮仅用合成 4 页 PDF 验证云端链路，真实论文质量仍需抽查；超时或文件限制会透明返回降级原因。
本机 MinerU CLI 未发表稿、敏感文档、云端不可用或要稳定复现 本地推理，不依赖 MinerU 云端账号；输出 ZIP 能保留页级结构数据 首次需要下载模型；Standard 模型冷启动较慢；mineru-kit parse 不缓存解析结果，须保存并复用产物。
本机 MinerU 常驻 V1 API 高频批量解析，希望只加载一次模型 服务常驻可复用已加载模型，通过 V1 Tasks API 做异步任务；应只监听 127.0.0.1 read4all 当前客户端没有 MINERU_API_URL 配置，且固定使用云端 V4；不能只改 URL，需适配 V1 Tasks API 和认证/轮询/下载协议。

MinerU 4.1 官方文档显示 Windows x64 使用 ONNX/DirectML 或 CPU，并把本机 API 作为 V1 Tasks 服务。本机已确认 RTX 3060 Ti GPU 路径有效。若以后接入常驻服务，先独立验证 /v1/health、单 PDF Tasks、轮询、ZIP 下载、超时恢复和并发限制，再把 read4all 客户端迁移到 V1；不要把云端 V4 的 /api/v4/file-urls/batch 地址误当成本机 V1 接口。

云端认证与下载链路复核

当前凭据

早先的 read4all 云端请求在 get_upload_url 阶段返回 401，旧凭据已被新凭据替换。2026-11-06 的真实云端冒烟测试完成了 MinerU V4 上传、轮询、ZIP 下载、内容缓存和 Markdown 直读，证明当前 read4all 配置中的 token 可用。密钥只保存在本机 Codex 配置，不写入仓库或科研文档。

解析结果下载曾因代理网络下的 SSL 失败而中断。read4all 现先按系统代理下载，再尝试直连 requests 和系统 curl；错误信息不包含有签名的下载 URL。当前本机 MCP 配置已改为从 read4all 源码目录启动。Codex 当前进程可能仍持有更新前的 MCP 工具清单；重启 Codex 后才能从活动连接看到 read_markdown 新工具。源码本地运行和云端请求已独立验证通过。

SSO 页面打不开或登录后循环

此前的 SSO 故障诊断仍可用于之后重新登录：本机经 HTTPS 代理访问登录页 TLS 握手失败，绕过代理直连 HTTP 200。若需重新进入 MinerU Token 页面，先让浏览器对 sso.openxlab.org.cn 与 mineru.net 直连，或临时关闭代理后再登录。当前 API token 已通过请求验证，因此这不是当前解析的阻塞点。

如果登录页可打开、认证成功但跳回 MinerU 后仍显示未登录，仍需按上游 SSO 问题继续排查；不要把网页登录状态与已验证的 API 请求状态混为一谈。

Zotero 本机 API 与卡顿排查

本轮检查中，普通 PowerShell 请求 Zotero 的 127.0.0.1:23119 API 被本机 HTTP 代理转发后返回 502；curl 显式绕过代理后，Connector ping 和 Zotero API 都返回 200。当前 shell 有 HTTP_PROXY/HTTPS_PROXY 指向 127.0.0.1:7897，未发现 NO_PROXY。这个结果可解释某些 MCP/外部客户端报告“Zotero API 不响应”，但不能单独证明 Zotero PDF 阅读器自身卡顿。

同一时段 Zotero 主进程约 603 MB 常驻内存，4 秒采样 CPU 增量为 0；zotero.sqlite 约 6.7 MB、fulltext.sqlite 约 6.8 MB、WAL 约 2.1 MB。它们没有显示数据库膨胀或持续高 CPU 证据。没有删除 Zotero 缓存、全文索引、数据库或附件；批量清缓存可能造成重建索引或丢失插件诊断资料。

若 AI/MCP 客户端访问本机 Zotero API，需让该客户端进程对 127.0.0.1、localhost 和 ::1 绕过 HTTP(S) 代理。要进一步定位 UI 卡顿，应在复现卡顿时单独记录 Zotero 主窗口、PDF 阅读器标签、具体插件和进程 CPU/内存；不要把代理造成的 API 502 与 Zotero 阅读器性能问题混为一谈。

Zotero 内阅读体验边界

LLM for Zotero 是本项目最终选择的 Zotero 内 AI 侧栏/Agent。上游 v3.9.16 支持在 Zotero 中进行论文问答和章节精读、展示来源并跳回原文；v3.9.11 起可同时保留侧栏与独立窗口中的不同会话。插件还能用 MinerU 为 AI 生成结构化 Markdown 和章节/页码索引。

上游将 MinerU 缓存定义为 AI 上下文，不是翻译后 PDF 或第二套人工阅读界面。官方功能文档目前没有把“全文双语 PDF 排版阅读”列为已支持功能，因此不应把章节问答/聊天翻译描述成与原 PDF 同步的双栏全文翻译。阅读原文仍用 Zotero PDF 或 Zotero 10 Reading Mode；公式、表格、图表和脚注必须回到原 PDF 页核验。

read4all 供 Codex 直接读取 Markdown，与 LLM for Zotero 的插件内缓存相互独立。本轮没有验证 LLM for Zotero 能调用 Codex 的 read4all MCP 工具，因此两条 AI 阅读路径不声称已打通。MinerU 解析时间、LLM 回复延迟和阅读器性能是不同环节；提高解析缓存命中率不会消除模型生成时间。

已知限制与待办

  1. 云端链路只在合成测试 PDF 上验证通过；真实课题论文的双栏顺序、公式、表格、图注和脚注仍需逐项抽查。
  2. read4all 目前没有本机 MinerU V1 Tasks API 适配，也没有将 MinerU middle JSON 作为公共读取工具返回；本机 MinerU CLI ZIP 仍需保留 middle JSON 才能做精确页码回查。
  3. Zotero 内置 MinerU 缓存和 read4all 文件缓存并不共享。避免双边同时自动解析同一大批附件，以免重复上传或计算。
  4. LLM for Zotero v3.9.16 的安装版本、插件内 MinerU token、自动解析开关、Agent 写入审批与会话窗口需在 Zotero 实机确认；本轮只验证了 read4all 侧的云端接口。
  5. 原 PDF 和 Zotero 元数据未被本轮解析测试修改；解析产物不覆盖原 PDF。AI 写回笔记或元数据前仍需检查来源和审批卡片。
