文献检索与 Zotero 补全经验

记录日期：2026-11-05。本文总结本项目 EC × LLM × 炼化调度文献库的修复流程，供后续扩展专题或复核附件时复用。它是工作记录和质量控制方法，不代表已完成系统综述。

面向后续检索、阅读和 AI 协作的完整流程见Zotero 与 AI 辅助文献工作流。

本轮结果与边界

  • Zotero 项目包含六个子集合、386 条活动记录。父集合没有直接条目。完整逐条状态见文献索引清单；阅读优先级见推荐阅读清单。
  • 当前有 167 条记录带 PDF 附件，共 168 个 PDF 文件。文件均在 Zotero storage 中存在。新增或替换的开放 PDF 已按题名、作者或 DOI 与来源核验；既有附件仍有一部分只确认文件存在，不能据此声称 386 条全部逐篇核对过。
  • 108 个 PDF 有内置目录；另为 60 个 PDF 建立或修复了 Jasminum 大纲，并校验 sidecar 的 Zotero 附件 itemID 和页码。最后一份 PDF 是无文字层的扫描件；我逐页渲染后人工核对章节名，再用物理页码写入大纲，没有伪造 PDF 文本层。
  • 本轮新增 3 条 Zotero 记录：EoH、2026 年 LLM × EA 综述、其相关但独立的 2024 arXiv 预印本。ReEvo 原本已在文库中，补齐标签和代码链接，没有重复导入。EoH 的 Zotero 类型已从误导性的 journalArticle 改为 conferencePaper，会议名保存在 proceedingsTitle 字段。
  • 386 条记录目前都至少有 4 个标签。对 10 条原先标签较少的重点文献追加了主题标签，保留已有标签；没有用批量覆盖替换原标签。
  • 全量索引给 386 条记录都填写代码状态；其中 42 条给出经核验的论文代码、基准/工具或参考实现链接，其余标注未找到可核验代码或不适用。
  • 对照 PDF 封面发现 10 个旧附件错配到不同论文，另有 ABEM 2023 条目挂着 2018 年另一篇同名缩写论文。10 个错配附件和旧 ABEM PDF 均通过 Zotero CLI 移入回收站，尚可恢复；ABEM 已替换为 UTS 机构仓储中的准确正式稿。
  • 当前 PDF 覆盖率为 167/386（43.3%）。未取得全文的高优先级条目逐项列在索引；期刊付费墙、仓储不可用或下载失败时，不用来源不明镜像代替。

可复用的检索和补全文献流程

1. 先盘点记录，再按 DOI 查来源

  1. 导出目标集合的完整条目、附件和标签，按 Zotero key 去重；确认集合和记录数，避免只查到父集合而漏掉子集合。
  2. DOI 优先；无 DOI 时用准确题名、作者、年份交叉确认。先看出版方页面，再看作者主页、机构仓储和可信预印本平台。OpenAlex、Unpaywall 适合发现候选来源，不应直接当作附件身份验证结果。
  3. 对预印本、作者接受稿和正式出版版分别记录版本关系。比如 2026 年期刊综述 CVMFASX3 与 arXiv:2410.20848 YW4YDR3P 是相关但独立的记录；不能把 2024 预印本 PDF 冒充成 2026 期刊 PDF。

2. 先验明 PDF 身份和授权，再挂附件

  • 下载后检查文件可读、页数合理，确认首页题名、作者至少与 Zotero 条目相符；有 DOI 时再核对 DOI。文件名、搜索结果摘要或标题词重合都不能单独证明它是正确 PDF。
  • 优先使用出版方开放版本、作者主页、机构知识库、arXiv 作者稿。记录发布方、版本、URL 和许可信息；付费墙页面、403 或请求超时不等于可以换用来历不明的镜像，也不应尝试绕过访问控制。
  • 用 CLI 将经核对的 PDF 关联到准确条目，再查附件路径和集合覆盖。发现错配时移入 Zotero 回收站保留恢复能力；不要清空回收站，不通过直接改数据库删除。
  • 本轮教训：旧批量补 PDF 流程曾出现只凭候选链接挂错文件的情况。本轮没有重跑旧 pdf_backfill.py；今后避免只按题名词重合或 OpenAlex 首个 URL 自动挂附件。

3. 大纲与标签分别修复

  • 先查 PDF 是否已有原生书签/目录。没有时从 PDF 文本或视觉页面提取实际章节标题，写入附件 storage 下的 jasminum-outline.json；每个 sidecar 的 info.itemID 必须是该 PDF 附件的内部 itemID，page 使用 PDF 的 1 起始物理页码。
  • 用 PyMuPDF 可读 PDF 文字、页数和目录；扫描件或无法可靠识别的文件应标注 OCR/人工复核，不要把正文句子、伪代码行、参考文献编号当成章节标题。
  • 标签采用追加方式保留已有分类标签和主题词。使用 edit --add-tags，不要用会覆盖原有 tags 的整列替换；标签大小写、同义词和中英文需尽量一致。

4. 逐条记录代码链接，分清代码和资源

索引里每条记录都有代码状态。只在论文正文、作者仓库或可信项目页面明确对应时标为论文代码；基准测试套件、软件框架、数据集、综述配套文献表和通用参考实现均用对应类型说明。不能核验时写“未找到可核验的论文对应代码”，不要把 PDF 参考文献中的任意 GitHub URL 误当作本文代码。

5. 完成后做可复查的覆盖审计

逐集合重新运行 coverage；对 PDF 检查 storage 文件存在；对 sidecar 检查 JSON、itemID、页码范围和大纲非空；检查新增记录无重复，错误附件仍可在回收站恢复。将未完成原因和可用官方入口写入索引，而不是只写“失败”。

Zotero CLI 与本地 API 用法

本项目使用本机 zotero-cli 与 Zotero 桌面端/本地文库协作。先看实际 CLI 帮助，再按以下模式执行；集合 key 和条目 key 均从当前库盘点获取：

zotero-cli --json get collection-items DNP95A8S --detail full --limit 500
zotero-cli --json coverage --collection MTNTFETE --limit 500
zotero-cli path <ITEM_KEY>
zotero-cli attach <ITEM_KEY> --file <已核对的PDF路径>
zotero-cli edit <ITEM_KEY> --add-tags "surrogate-assisted optimization,black-box optimization"

本机 Local API 可用于需要的自动化读取/写入，但写请求须遵守本机 Zotero 服务的 Zotero-Server-ID 校验要求。API key、OpenAlex key、账号凭据只从用户本机配置或环境变量读取，绝不写入项目文档、日志或导出文件。批量修改前先小批量执行并重新导出核对；删除操作优先使用 CLI 的可恢复流程，避免绕过 Zotero 的回收站语义。
